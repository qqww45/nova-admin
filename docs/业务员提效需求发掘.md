# 业务员提效需求发掘（金蝶同步 / 对账 / 跟单 / 催款 / 报数 / 协同）

> 本文是业务员视角的产品级需求发掘总表，覆盖**不只对账**的日常全景：跟单、催款、发货核对、
> 客户查询、报数、异常排查、移动端/桌面端协同。2026-11-03 第二轮发掘，合并并取代
> 此前《金蝶对账-业务员提效建议清单.md》（对账向内容已并入 §2/§6）。
>
> 每条需求标注：场景/痛点、方案、依赖数据、优先级（P0~P2）、价值与难度、可搭车的现网模块，
> 以及结论（**强烈建议做 / 可试点 / 暂不做**）。

## 1. 现有能力盘点（需求的地基，先盘清楚再谈加什么）

| 能力 | 现状 | 对业务员的意义 |
|------|------|----------------|
| 内部订单/出货 | 订单（明细 `qtyOrdered/qtyShipped/qtyOpen`，状态服务端重算；页面已有关键字/状态/**仅看未出货**过滤） | 跟单的事实来源 |
| 内部应收闭环 | 对账单快照 → 签发 → 客户确认（回签）/ 标记差异 → 导出台账；收款登记 + 客户期初应收 | 催款的事实来源 |
| 数据体检（内部） | 重复客户 / 缺料号 / 数量异常 / 税率异常 / 无源出货（异常池补挂订单） | 内部数据质量 |
| 金蝶同步（KD 域） | 采集器上行 → kd_customer / kd_outbound(+line) → 对账单（实时计算 + 单客户/全局导出）+ 数据查看三页 + 数据体检条幅 | 对客户报数的事实来源 |
| 采集器运维 | 绑定/令牌/轮换/吊销、指令轮询（sync.now / config.reload / token.revoke / client.update）、**在线状态列**、同步批次 | "数据没上来"自查 |
| 基建 | 邮件（EmailService）、无 POI Excel 读写、动态菜单（发页面不用发版）、权限/数据权限（业务员仅本人）、字段映射后台配置 | 搭车轮 |

**结构性事实**：内部系统与金蝶侧是**两套客户体系、两个出货口径**（本系统出货单 vs 金蝶出库单），
目前互不感知。多数"客户说对不上"的争议，本质是这两个口径或口径内部的数据质量没对齐。

## 2. 已落地（随需求发掘直接实现，不再列需求）

| 项 | 说明 |
|----|------|
| 规格型号断链修复 | 金蝶采集→上行→落库→对账单/数据页全链路此前 spec 永远为空，已修复并带回归测试 |
| 单客户一键导出对账单 | 明细抽屉按钮，复用导出接口 |
| 采集器在线状态 | 绑定页按心跳判定在线/离线时长 |
| 对账单数据体检条幅 | `GET /kd/statement/health`：本期无分录 N 张（退表头金额）/ 作废 M 张 / 失效 K 张，条幅直显，"金额对不上先看这里" |
| 一键复制报数 | 汇总行复制成一行文本（客户/期间/单数/金额），直接微信发客户 |
| 日期快捷选择 | 本月 / 上月 / 近 30 天 / 本季度 |

## 3. 需求清单（按业务场景分组）

### 3.1 跟单（订单执行进度）

#### R1 催单清单（按客户聚合的未出订单）——**强烈建议做**

- **场景/痛点**：订单页已有「仅看未出货」，但业务员催单的真实动作是"按客户要货"：
  对着 A 客户问"我下的单哪些还没交？"需要一页按客户聚合的未出明细（订单号/型号/下单数/已出/未出/预计交货），
  打印或截图就能去催生产、回客户。现在要逐单点开、自己拿笔记。
- **方案**：报表页新增「未交清单」：输入客户（或全部）→ 按 `qtyOpen > 0` 聚合订单明细，按客户分组导出。
  纯读侧，复用订单查询与 Excel 导出。
- **依赖数据**：`biz_order` 明细（已有）。
- **优先级**：P1；**价值高 / 难度低**；**可搭车**：报表页（`biz/report`）、客户出货汇总（同是按客户聚合）。

### 3.2 催款 / 应收

#### R2 客户应收速览（余额 + 账龄一页看）——**强烈建议做**

- **场景/痛点**：催款前业务员要回答"这个客户还欠多少、欠的是哪几个月的账"。现在数据都在
  （期初 + 出货 - 收款 + 未确认差异），但分散在对账单详情里，没有"我的客户欠款排行"视图，
  催款优先级全凭记忆。
- **方案**：报表页新增「客户应收」：客户维度余额与最近确认时间，支持按余额/账龄排序。
  口径复用对账单预览的现成计算（期初 + 本期出货 − 退货 − 收款）。
- **依赖数据**：`biz_statement`（期初/快照/确认状态）、`biz_receipt`、出货明细（全部已有）。
- **优先级**：P1；**价值高 / 难度中**（口径已存在，主要是聚合与页面）；**可搭车**：对账单预览逻辑、客户出货汇总。
- **注意**：内部应收与 KD 对账单（只报出货）是两套口径，页面上要写明"应收口径 = 内部确认流"，
  防止与金蝶对账数字混看。

#### R3 月度对账提醒（邮件）——**可试点**

- **场景/痛点**：月底容易忘：忘了出内部对账单、忘了催客户回签、忘了导金蝶对账单。
- **方案**：每月 1 日定时邮件给业务员：上月各客户对账状态（已签发未确认的客户清单 + 待导出提示）。
- **依赖数据**：对账单状态 + 邮件基建（EmailService 已有）；**缺**：定时任务基建（Spring `@Scheduled`，现网没有先例，需一并落一个最小调度配置）。
- **优先级**：P2；**价值中 / 难度中**；**可搭车**：邮件、对账单查询。

### 3.3 发货核对（两个出货口径对齐）

#### R4 金蝶客户 ↔ 内部客户映射——**强烈建议做（两口径联动的前置）**

- **场景/痛点**：本系统客户（`biz_customer`）与金蝶客户内码是两套 ID；目前"金蝶出货 vs 内部出货"
  的任何核对都要业务员人肉对客户名。映射做一次，后续所有联动（R5、客户 360）才有地基。
- **方案**：新增映射维护页（金蝶客户 ↔ 内部客户，一人一个账套范围）；用体检报告已有的
  "名称标准化匹配"给候选建议，人工确认（不能全自动：金蝶客户名与内部客户名常有全半角/后缀差异）。
- **依赖数据**：`kd_customer`、`biz_customer`（均已有）。
- **优先级**：P1；**价值高（解锁 R5）/ 难度中**；**可搭车**：客户页、体检报告的重复客户检测逻辑。

#### R5 两口径金额对照页——**可试点（依赖 R4）**

- **场景/痛点**：客户拿着金蝶对账单问业务员"你们系统里也是这个数吗？"——现在两边数字没有并排视图，
  对不上时要在两个页面间手抄比对。
- **方案**：按客户 + 月份并排展示：金蝶出库金额（KD 对账单口径）vs 内部出货金额（确认流口径），
  差异行标红并给出跳转（金蝶数据页 / 内部出货页）。差异常见原因（无分录、作废、无源出货、
  时间性差异）给出提示文案。
- **依赖数据**：R4 映射 + kd_outbound_line + 内部出货明细。
- **优先级**：P2（先有 R4 再做）；**价值高 / 难度高**（差异解释是产品难点，先人工解释、逐步固化规则）；
  **可搭车**：KD 数据体检条幅（差异提示复用）、报表页。

### 3.4 客户查询 / 报数

#### R6 客户 360 轻量版——**可试点**

- **场景/痛点**：跟一个客户要开 4 个页面（订单/出货/对账单/金蝶数据），电话里客户一问就要来回切。
- **方案**：不做大而全的 360（易烂尾）；先做"客户页行内展开"：点客户名弹出侧栏，展示
  该客户近 90 天订单（未出汇总）、内部对账状态、金蝶出货汇总三张小卡片，各带"去看详情"跳转。
- **依赖数据**：均已有；KD 侧卡片在无 R4 映射前按客户名模糊匹配并标注"可能串户，请确认"。
- **优先级**：P2；**价值中 / 难度中**；**可搭车**：客户页、ProTable 展开行（出库数据页已有同款交互）。

#### R7 金蝶对账单补客户编码列——**强烈建议做**

- **场景/痛点**：金蝶客户编码（`kd_customer.kd_number`）已同步但汇总/导出不显示；客户重名时
  业务员靠名称核数容易串户，客户自己也按编码对账。
- **方案**：汇总/明细/导出各加「客户编码」列，按「账套 + 客户内码」回查 `kd_customer`。
- **依赖数据**：`kd_customer`（已有）；**优先级**：P1；**价值中高 / 难度低**；**可搭车**：KD 对账单链路。

### 3.5 异常排查

#### R8 双水位增量（FModifyDate）——**强烈建议做（数据正确性优先）**

- **场景/痛点**：现在增量按 `FDate` 过滤，**改过的历史单抓不到**（改单号/改数量后网页数字与
  金蝶不一致，业务员被客户问住）；全量兜底又慢又依赖人触发。这是同步链路当前最大的数据正确性缺口。
- **方案**：见方案文档 §3.1 目标形态——`FModifyDate − 15min` 水位 + 每月按 `FDate` 回看 30 天；
  服务端水位语义从"本地完成时间"切换为金蝶修改时间（表结构已预留）。
- **依赖数据**：`kd_binding` 水位列、`kd_outbound.kd_modify_time`（已建）；桌面端 `sync/runner.ts`。
- **优先级**：P1（原 P2 上调：体检条幅上线后，"改单没同步上来"会成为最高频的对不上原因）；
  **价值高 / 难度中**；**可搭车**：无（客户端发版 + 灰度开关）。

#### R9 字段自检结果回传——**强烈建议做**

- **场景/痛点**：现场跑一次「字段自检」拼出的分录字段集，现在要业务员把报告复制给运维、
  运维手抄进后台配置页，一来一回一两天。采集器明明已经能直连服务端。
- **方案**：自检完成后提供「上传字段集到平台」按钮：写 `kd_field_mapping`（按 binding），
  页面提示"已通知运维确认"。管理端配置页已有查看/编辑能力，闭环现成。
- **依赖数据**：`kd_field_mapping`、绑定令牌（已有）。
- **优先级**：P1；**价值高（砍掉一次现场往返）/ 难度低**；**可搭车**：字段映射配置页、`config.reload` 指令。

### 3.6 移动端 / 桌面端协同

#### R10 移动端轻报数（对账单页窄屏适配）——**可试点**

- **场景/痛点**：业务员在外面见客户，掏手机打开后台——Element Plus 桌面布局在手机上基本不可用，
  最刚需的"看客户出货汇总 + 复制报数 + 发对账单"做不了。
- **方案**：不做原生 App、不改全部页面；只对「KD 对账单汇总」做窄屏适配（列表简化为卡片、
  条幅与复制报数按钮保留），见客户场景 80% 的需求就是这一页。
- **依赖数据**：无新数据；**优先级**：P2 试点（先给 1~2 个业务员用，看真实使用频率再决定投入）；
  **价值中高 / 难度中**（布局改造 + 触控交互）；**可搭车**：现有页面改造，无新接口。

#### R11 采集器托盘常驻 + 定时同步——**强烈建议做（数据断档的根治）**

- **场景/痛点**：电脑重启后采集器不启动，数据断档数天没人发现（在线状态列已让断档可见，
  但根治要靠常驻 + 定时）。方案文档 §12.3 已列未实施。
- **方案**：Electron tray + 定时 `runSync`；多台机器重复全量问题用服务端水位协商（绑定行已有水位）。
- **优先级**：P1；**价值高 / 难度中**（托盘交互 + 休眠实测）；**可搭车**：指令通道（定时同步与
  `sync.now` 共用同一流程）。
- **附带**：同步完成后托盘气泡通知"本次上行 客户 N / 出库 M / 分录 K"（成本低，一起做）。

#### R12 对账单 PDF / 盖章模板——**暂不做**

- **理由**：现网明确"客户要求盖章 PDF 时再接模板引擎"（方案 §12.3）；Excel 导出已覆盖当前客户诉求。
  先收集 1~2 个客户的真实样板，避免做一版没人用的模板。触发条件：有客户明确拒绝 Excel 对账时启动。

### 3.7 暂不做项（及理由，避免反复讨论）

| 项 | 理由 |
|----|------|
| WebSocket 替换指令轮询 | 方案 §12.2 第 8 条已论证：现场反向代理 + 休眠场景轮询更可靠 |
| 跨业务员数据合并 / 上级看下级 | 方案 §1 明确不做，权限模型（仅本人）不为其留口子 |
| KD 对账单接入 `biz_statement` 应收口径 | 两套客户体系硬接会污染应收账龄（方案 §12.2 第 7 条），R4/R5 的映射路线是正解 |
| 库存模块 | 现网无库存数据源；金蝶侧同步库存需新任务类型与大量字段映射，价值待验证，暂不立项 |
| 应收/收款单金蝶同步 | 有价值（对完货看回款），但优先级低于把出货口径对齐（R8）；作为"加任务不发版"机制的第二个试点保留在 P2 |
