# 业务员提效需求发掘（金蝶同步 / 对账 / 跟单 / 催款 / 报数 / 协同）

> 本文是业务员视角的产品级需求发掘总表，覆盖**不只对账**的日常全景：跟单、催款、发货核对、
> 客户查询、报数、异常排查、移动端/桌面端协同。2026-11-03 第二轮发掘，合并并取代
> 此前《金蝶对账-业务员提效建议清单.md》（对账向内容已并入 §2/§6）。
>
> 每条需求标注：场景/痛点、方案、依赖数据、优先级（P0~P2）、价值与难度、可搭车的现网模块，
> 以及结论（**强烈建议做 / 可试点 / 暂不做**）。

## 1. 现有能力盘点（需求的地基，先盘清楚再谈加什么）

| 能力 | 现状 | 对业务员的意义 |
|------|------|----------------|
| 内部订单/出货 | 订单（明细 `qtyOrdered/qtyShipped/qtyOpen`，状态服务端重算；页面已有关键字/状态/**仅看未出货**过滤） | 跟单的事实来源 |
| 内部应收闭环 | 对账单快照 → 签发 → 客户确认（回签）/ 标记差异 → 导出台账；收款登记 + 客户期初应收 | 催款的事实来源 |
| 数据体检（内部） | 重复客户 / 缺料号 / 数量异常 / 税率异常 / 无源出货（异常池补挂订单） | 内部数据质量 |
| 金蝶同步（KD 域） | 采集器上行 → kd_customer / kd_outbound(+line) → 对账单（实时计算 + 单客户/全局导出）+ 数据查看三页 + 数据体检条幅 | 对客户报数的事实来源 |
| 采集器运维 | 绑定/令牌/轮换/吊销、指令轮询（sync.now / config.reload / token.revoke / client.update）、**在线状态列**、同步批次 | "数据没上来"自查 |
| 基建 | 邮件（EmailService）、无 POI Excel 读写、动态菜单（发页面不用发版）、权限/数据权限（业务员仅本人）、字段映射后台配置 | 搭车轮 |

**结构性事实**：内部系统与金蝶侧是**两套客户体系、两个出货口径**（本系统出货单 vs 金蝶出库单），
目前互不感知。多数"客户说对不上"的争议，本质是这两个口径或口径内部的数据质量没对齐。

## 3. 需求清单（按业务场景分组）

### 3.1 跟单（订单执行进度）

#### R1 催单清单（按客户聚合的未出订单）——**强烈建议做 → ✅ 已落地**

- **场景/痛点**：订单页已有「仅看未出货」，但业务员催单的真实动作是"按客户要货"：
  对着 A 客户问"我下的单哪些还没交？"需要一页按客户聚合的未出明细（订单号/型号/下单数/已出/未出/预计交货），
  打印或截图就能去催生产、回客户。现在要逐单点开、自己拿笔记。
- **方案**：报表页新增「催单清单」标签：按 `qtyOpen > 0` 聚合订单明细，取消行排除，行序先客户后下单时间，预计交货过期标红。
- **依赖数据**：`biz_order` 明细（已有）。
- **优先级**：P1 → **已落地**（`GET /biz/report/open-items`，权限复用 `biz:report:view`，无新增菜单/迁移）；**搭车**：报表页。

### 3.2 催款 / 应收

#### R2 客户应收速览（余额 + 最近往来一页看）——**强烈建议做 → ✅ 已落地**

- **场景/痛点**：催款前业务员要回答"这个客户还欠多少、欠的是哪几个月的账"。数据都在
  （期初 + 出货 - 收款），但没有"我的客户欠款排行"视图，催款优先级全凭记忆。
- **方案**：报表页新增「客户应收」标签：客户维度期末应收倒序，最近出货/收款时间标注"欠了多久"。
  口径复用对账单聚合引擎（`StatementGenerator` 单一实现），一次拉全量内存分组避免 N+1。
- **依赖数据**：`biz_statement`（期初）、`biz_receipt`、出货明细（全部已有）。
- **优先级**：P1 → **已落地**（`GET /biz/statement/receivable-summary`，权限复用 `biz:statement:list`）；**搭车**：对账单聚合逻辑、报表页。
- **注意**：页面已写明"应收口径 = 内部确认流（不含金蝶数据）"，防止与 KD 对账数字混看。

#### R3 月度对账提醒（邮件）——**可试点 → ✅ 已落地**

- **场景/痛点**：月底容易忘：忘了出内部对账单、忘了催客户回签、忘了导金蝶对账单。
- **方案与落地**：`@Scheduled` 每月 1 日 08:00（Asia/Shanghai）按录入人分组发上月对账待办
  （草稿未签发 / 已签发待客户确认清单，含客户名、单号、期末应收），并提示导出金蝶对账单
  核对出货口径；`sys_config` 标记幂等（当天服务重启不重发）；`admin.statement-reminder.enabled`
  默认关、仅生产开启（dev/staging 邮件通道本就未配置）；无邮箱用户跳过且不中断他人。
- **依赖数据**：对账单状态 + 用户邮箱 + 邮件基建（均已有）。

### 3.3 发货核对（两个出货口径对齐）

#### R4 金蝶客户 ↔ 内部客户映射——**强烈建议做（两口径联动的前置）→ ✅ 已落地**

- **场景/痛点**：本系统客户（`biz_customer`）与金蝶客户内码是两套 ID；目前"金蝶出货 vs 内部出货"
  的任何核对都要业务员人肉对客户名。映射做一次，后续所有联动（R5、客户 360）才有地基。
- **方案与落地**：`V21` 迁移（表 + 菜单 48 + 权限 `kd:customer-mapping:{list,edit}` 授予 role 1/2/3）；
  唯一键 owner+acct+kdFid；三接口（列表 / 自动建议 / 人工保存）；自动建议按名称标准化
  **唯一命中**才生成、同名歧义留人工（金蝶客户名与内部客户名常有全半角/后缀差异，不做全自动）；
  前端「金蝶同步 → 客户映射」页：三态展示（未匹配/建议待确认/已确认）+ 行内搜索内部客户即确认；
  业务员强制本人隔离，管理员可代维护但必须显式指定归属业务员。
- **依赖数据**：`kd_customer`、`biz_customer`（均已有）。

#### R5 两口径金额对照页——**可试点（依赖 R4）**

- **场景/痛点**：客户拿着金蝶对账单问业务员"你们系统里也是这个数吗？"——现在两边数字没有并排视图，
  对不上时要在两个页面间手抄比对。
- **方案**：按客户 + 月份并排展示：金蝶出库金额（KD 对账单口径）vs 内部出货金额（确认流口径），
  差异行标红并给出跳转（金蝶数据页 / 内部出货页）。差异常见原因（无分录、作废、无源出货、
  时间性差异）给出提示文案。
- **依赖数据**：R4 映射 + kd_outbound_line + 内部出货明细。
- **优先级**：P2（先有 R4 再做）；**价值高 / 难度高**（差异解释是产品难点，先人工解释、逐步固化规则）；
  **可搭车**：KD 数据体检条幅（差异提示复用）、报表页。

### 3.4 客户查询 / 报数

#### R6 客户 360 轻量版——**可试点**

- **场景/痛点**：跟一个客户要开 4 个页面（订单/出货/对账单/金蝶数据），电话里客户一问就要来回切。
- **方案**：不做大而全的 360（易烂尾）；先做"客户页行内展开"：点客户名弹出侧栏，展示
  该客户近 90 天订单（未出汇总）、内部对账状态、金蝶出货汇总三张小卡片，各带"去看详情"跳转。
- **依赖数据**：均已有；KD 侧卡片在无 R4 映射前按客户名模糊匹配并标注"可能串户，请确认"。
- **优先级**：P2；**价值中 / 难度中**；**可搭车**：客户页、ProTable 展开行（出库数据页已有同款交互）。

#### R7 金蝶对账单补客户编码列——**强烈建议做 → ✅ 已落地**

- **场景/痛点**：金蝶客户编码（`kd_customer.kd_number`）已同步但汇总/导出不显示；客户重名时
  业务员靠名称核数容易串户，客户自己也按编码对账。
- **方案与落地**：汇总/明细/导出两个 sheet 全部补「客户编码」列，按「账套 + 客户内码」回查 `kd_customer`
  （内码跨账套冲突防串户）；复制报数文本一并带编码。
- **依赖数据**：`kd_customer`（已有）；**已落地**（无迁移，跟随 M7 批次）。

### 3.5 异常排查

#### R8 双水位增量（FModifyDate）——**强烈建议做 → ✅ 已落地**

- **场景/痛点**：此前增量按 `FDate` 过滤，**改过的历史单抓不到**（改单号/改数量后网页数字与
  金蝶不一致，业务员被客户问住）；全量兜底又慢又依赖人触发。这是同步链路当时最大的数据正确性缺口。
- **方案与落地**：`FModifyDate − 15min` 主水位 + 超 30 天未回看时按 `FDate` 回看 30 天；
  `FModifyDate` 可用性按账套探测并缓存（不可用自动降级回旧行为）；显式日期重拉与首次全量语义保留；
  上行 `modifyTime` 改用金蝶修改时间。桌面端 v4 本地迁移 + 同步页日期框变可选。
- **依赖数据**：`kd_binding` 水位列、`kd_outbound.kd_modify_time`、桌面 `sync/filter.ts`。
- **上线注意**：随下个采集器版本发布；发布前老客户端仍按 FDate 逻辑（行为不变）。

#### R9 字段自检结果回传——**强烈建议做 → ✅ 已落地**

- **场景/痛点**：现场跑一次「字段自检」拼出的分录字段集，要业务员把报告复制给运维、
  运维手抄进后台配置页，一来一回一两天。采集器明明已经能直连服务端。
- **方案与落地**：自检报告区「上传到对账平台」按钮 → `POST /kd/sync/mapping`（采集器令牌，
  写本绑定 `kd_field_mapping`，key 与配置页约定一致、空值跳过）；运维确认后 `config.reload` 生效。
- **依赖数据**：`kd_field_mapping`、绑定令牌（已有）。

### 3.6 移动端 / 桌面端协同

#### R10 移动端轻报数（对账单页窄屏适配）——**可试点 → ✅ 已落地**

- **场景/痛点**：业务员在外面见客户，掏手机打开后台——Element Plus 桌面布局在手机上基本不可用，
  最刚需的"看客户出货汇总 + 复制报数 + 发对账单"做不了。
- **方案与落地**：不做原生 App、不改全部页面；`useIsMobile`（matchMedia 768px）判定窄屏，
  对账单页自动切换卡片视图——快捷日期 chips、客户卡片（编码/账套/单数/金额）、
  明细/复制报数/单客户导出、简洁分页；明细抽屉移动端全宽；体检条幅保留。
  桌面端视图完全不变。后续按真实使用频率决定是否扩到其它页面。

#### R11 采集器托盘常驻 + 定时同步——**强烈建议做 → ✅ 已落地**

- **场景/痛点**：电脑重启后采集器不启动，数据断档数天没人发现（在线状态列已让断档可见，
  但根治要靠常驻 + 定时）。
- **方案与落地**：关窗隐藏到托盘（首次气泡提示）；托盘菜单显示/立即同步/开机自启开关/退出；
  每 2 小时自动同步并上行（有绑定才执行、业务锁让位、结果气泡提示）；开机自启默认开启。
  图标取自可执行文件，仅打包后生效（开发模式关窗即退）。
- **多机重复全量的顾虑**：已被 R8 双水位化解——增量按金蝶修改时间，多台机器重复执行幂等且代价低。

#### R12 对账单 PDF / 盖章模板——**暂不做**

- **理由**：现网明确"客户要求盖章 PDF 时再接模板引擎"（方案 §12.3）；Excel 导出已覆盖当前客户诉求。
  先收集 1~2 个客户的真实样板，避免做一版没人用的模板。触发条件：有客户明确拒绝 Excel 对账时启动。

### 3.7 暂不做项（及理由，避免反复讨论）

| 项 | 理由 |
|----|------|
| WebSocket 替换指令轮询 | 方案 §12.2 第 8 条已论证：现场反向代理 + 休眠场景轮询更可靠 |
| 跨业务员数据合并 / 上级看下级 | 方案 §1 明确不做，权限模型（仅本人）不为其留口子 |
| KD 对账单接入 `biz_statement` 应收口径 | 两套客户体系硬接会污染应收账龄（方案 §12.2 第 7 条），R4/R5 的映射路线是正解 |
| 库存模块 | 现网无库存数据源；金蝶侧同步库存需新任务类型与大量字段映射，价值待验证，暂不立项 |
| 应收/收款单金蝶同步 | 有价值（对完货看回款），但优先级低于把出货口径对齐（R8）；作为"加任务不发版"机制的第二个试点保留在 P2 |
