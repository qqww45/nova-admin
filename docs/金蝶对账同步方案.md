# 金蝶对账同步方案（桌面采集 + 后台业务）

> 状态：M1~M4 已实施（绑定/令牌、任务清单与批量上报、后台对账单与导出、指令通道、客户端双写）；数据查看页（客户/出库单/分录原始数据排查）已补齐；规格型号字段断链已修复；双水位增量、字段自检回传、托盘常驻与定时同步已实施（M7）；客户映射、移动端轻报数、月度对账提醒已实施（M8 试点批）
> 更新日期：2026-11-03
>
> 实施记录与偏差说明见文末 §12；业务员提效需求发掘（跟单 / 催款 / 报数 / 协同等，P0~P2）见《业务员提效需求发掘.md》。

## 1. 背景与目标

现有桌面工具（`desktop/`，前身独立仓库 `qqww45/hengzhang`）已能从金蝶 K3 Cloud 同步客户、销售订单、销售出库单并在本地生成对账单。但存在三个结构性问题：

1. **每次改功能都要发 88MB 安装包**，现场安装、验证成本高；
2. **金蝶字段名每家账套不同**（`FQty`/`FRealQty`、分录内码 `FEntryID`/`FEntity_FEntryID`），只能靠现场自检、手改 JSON，且客户环境往往拿不到 BOS 设计器；
3. 数据只存在本地 SQLite，换电脑/重装即丢，无法集中运维。

**目标**：桌面端退化为"通用采集器"，只负责把业务员自己在金蝶可见的数据增量同步上来；对账单及后续所有功能扩展都放在 nova-admin。

**使用维度**：业务员。每个业务员登录自己的金蝶账号，同步自己权限范围内的数据，只看自己的数据。

- 不做上级看下级、不做提成汇总、不做跨业务员重复数据合并；
- 数据权限只考虑"仅本人"（`data_scope = 4`）；
- 以金蝶数据为准，权限导致的数据残缺由业务员自行处理，系统不做补偿。

## 2. 总体架构

```
┌──────────── 客户机（Electron，采集器）────────────┐
│ 1. 金蝶登录（账号密码只存本机，safeStorage 加密） │
│ 2. 绑定 nova-admin 账号，持机器令牌               │
│ 3. 拉取「同步任务清单」→ 按清单增量采集 → 上报    │
│ 4. 本地 SQLite 仅作缓存与失败重试队列             │
│ 5. 只显示：连接状态 / 同步进度 / 上次同步 / 日志  │
└───────────────────┬───────────────────────────────┘
                    │ ① REST 批量上报（客户端 → 服务端）
                    │ ② WebSocket 指令（服务端 → 客户端）
┌───────────────────▼───────────────────────────────┐
│ nova-admin（Spring Boot + Vue3）                  │
│ · 绑定 / 令牌 / 账套管理                          │
│ · 数据落库（customer / outbound / outbound_line） │
│ · 字段映射与同步任务配置（改字段不再发版）        │
│ · 对账单生成 + Excel 导出 + 打印模板              │
│ · 复用现有：用户/角色/数据权限/日志/Knife4j       │
└───────────────────────────────────────────────────┘
```

关键取舍：

| 决策 | 结论 | 理由 |
|---|---|---|
| 采集方式 | 业务员各自同步（分散） | 拿不到全权限账号；且只服务业务员本人 |
| 数据隔离 | `owner_user_id` + `acct_id` | 一个业务员可连多个账套，数据需分开 |
| 权限 | 复用 `data_scope=4` | 无需新增权限模型 |
| 对账口径 | 只在服务端实现一份 | 避免客户端/服务端两套口径对不上 |
| 删除单 | 全量指令兜底 | 增量无法发现物理删除 |

## 3. 增量同步

### 3.1 水位字段

| 方案 | 做法 | 漏单风险 | 采用 |
|---|---|---|---|
| `FDate` | 按业务日期递增 | 改过的历史单抓不到 | 兜底 |
| `FModifyDate` | 按修改时间递增 | 低 | 首选（需自检验证存在） |
| 双水位 | `FModifyDate - 15min` 缓冲 + 每月按 `FDate` 回看 30 天 | 最低 | 目标形态 |

首次同步为全量（按日期分段，`StartRow/Limit=2000` 循环），之后走增量。

### 3.2 时序（顺序不能反）

```
1 读本地 last_watermark
2 分页拉金蝶
3 写本地缓存
4 批量上报 → 服务端返回 200（已落库）
5 才推进 last_watermark
```

`at-least-once` + 服务端幂等 upsert，断电/断网重跑安全。

### 3.3 作废与删除

| 情形 | 处理 |
|---|---|
| 单据作废 | 同步 `FCancelStatus`/`FDocumentStatus`，服务端软标记，页面可过滤 |
| 单据物理删除 | 后台下发 `sync.full` 全量指令，客户端重跑后由服务端按批次差集标记失效 |
| 数据残缺 | 以金蝶为准，不补偿 |

## 4. 双向触发

### 4.1 客户端 → 服务端（数据上行）

- 手动点击 / 定时自动 / 服务端指令，三种触发共用同一同步流程；
- 按实体分行上报：`/api/kd/sync/customer`、`/api/kd/sync/outbound`、`/api/kd/sync/outbound-line`；
- 每次上报携带 `batchId`，结束后回报批次结果（水位、行数、耗时、错误）。

### 4.2 服务端 → 客户端（指令下行）

| 指令 | 用途 |
|---|---|
| `sync.now`（可带 `full`） | 后台点"立即同步"；或用例：某业务员长期未同步 |
| `config.reload` | 字段映射/任务清单变更后，通知客户端重拉（**改字段不发版的关键**） |
| `token.revoke` | 离职/换电脑，远程吊销 |
| `client.update` | 提示升级 |

实现：客户端启动后建立 WebSocket（令牌认证），断线指数退避重连；WS 不可用时降级为 60s 轮询指令接口。

### 4.3 同步任务清单下发

客户端不再硬编码同步哪些单据，启动/收到 `config.reload` 时拉取：

```json
[
  { "formId": "BD_Customer",  "endpoint": "/api/kd/sync/customer",      "fieldKeys": "FCUSTID,FNumber,FName", "watermarkField": "FModifyDate" },
  { "formId": "SAL_OUTSTOCK", "endpoint": "/api/kd/sync/outbound",      "fieldKeys": "FID,FBillNo,FDate,...", "watermarkField": "FModifyDate" },
  { "formId": "SAL_OUTSTOCK", "endpoint": "/api/kd/sync/outbound-line", "fieldKeys": "FID,FEntity_FEntryID,...", "watermarkField": "FModifyDate" }
]
```

新增单据类型（如应收单）= 后台加一条任务 + 一张表 + 一个页面，**客户端不用发版**。

## 5. 身份与绑定

```
nova 用户（业务员） 1 ─── N  kd_binding（账套 acct_id + 金蝶账号 + 令牌）
```

- 绑定流程：nova 端登录 → 生成一次性绑定码（5 分钟有效）→ 客户端输入 → 换取机器令牌；
- 令牌：32 字节随机，DB 仅存 hash，支持刷新/吊销/查看最后使用；
- nova 密码不下发客户端；金蝶密码用 Electron `safeStorage` 加密存本机，不上行；
- 所有查询强制带 `owner_user_id = 当前登录用户`。

## 6. 数据模型

| 表 | 用途 | 唯一键 / 索引 |
|---|---|---|
| `kd_binding` | 绑定 + 令牌 + 各实体水位 | `uk(user_id, acct_id)` |
| `kd_sync_task` | 同步任务清单（formId/endpoint/fieldKeys/水位字段/启用） | 全局模板 + 按账套覆盖 |
| `kd_field_mapping` | 字段映射（客户采购订单号字段、列映射） | 按 binding |
| `kd_customer` | 客户 | `uk(owner_user_id, acct_id, kd_fid)` |
| `kd_outbound` | 出库单头 | `uk(owner_user_id, acct_id, fid)`；`idx(owner, fdate)` |
| `kd_outbound_line` | 出库分录 | `uk(owner_user_id, acct_id, entry_id)`；`idx(owner, outbound_fid)` |
| `kd_sync_batch` | 同步批次（水位/行数/状态/耗时） | 用于重放与排障 |

统一约定：

- 金额 `bigint` 存分、数量 `bigint` 存千分之一、单价 `bigint` 存分（与客户端 `amount_cents/qty_milli/price_cents` 一致）；
- 时间统一 ISO 字符串，SQLite / MySQL 均安全；
- upsert 使用 MyBatis-Plus `saveOrUpdate`（应用层先查后写），**不写原生 `ON CONFLICT` / `ON DUPLICATE KEY`**，切库零改动；
- Flyway 从 `V8__` 起新增，不动现有 `V1~V7`。

## 7. 服务端模块划分（对齐现有 DDD 四层）

| 层 | 内容 |
|---|---|
| interfaces | `SyncController`、`BindingController`、`MappingController`、`CommandController`（WS + 轮询）、`StatementController` |
| application | `SyncAppService`（幂等落库/水位校验/批次）、`CommandAppService`（指令下发、在线状态）、`StatementAppService` |
| domain | `Outbound`（聚合根 + `OutboundLine`）、`Customer`、`SyncBatch`、`Watermark`、`FieldMapping`、`StatementPolicy` |
| infrastructure | MyBatis Mapper、WebSocket 推送、令牌仓储 |

`StatementPolicy` 独立成领域服务：对账口径（按月汇总、页脚合计、抬头）只有一份实现。

## 8. 桌面端改造

移除：对账单页、Excel 导出、客户/月份筛选（M2 后由后台承担）。

新增：

- 绑定页（绑定码 / 令牌状态 / 解绑）；
- 状态页（连接信息、上次同步时间与行数、队列积压、最近日志）；
- 托盘常驻 + 开机自启 + 定时同步（每 N 小时 / 每天定点）；
- 本地 SQLite 降级为缓存 + 重试队列，恢复后自动补传；
- WebSocket 客户端 + 退避重连 + 指令执行器；
- 金蝶密码与令牌用 `safeStorage` 加密存储；
- 自动更新沿用 `electron-updater`（更新源见 §10）。

## 10. 仓库组织与发版

### 10.1 单仓库（monorepo）

```
nova-admin/
├─ admin-backend/      Spring Boot
├─ admin-frontend/     Vue3
├─ desktop/            桌面采集器（原 hengzhang 仓库，git 历史已并入）
├─ docs/
└─ .github/workflows/{deploy-backend, deploy-frontend, release-desktop}.yml
```

- 契约变更（同步 API、字段映射、WS 指令）一次提交覆盖三端，避免"后端改了客户端没跟上"；
- 原 `qqww45/hengzhang` 仓库保留为只读归档。

### 10.2 发版与自动更新

- 桌面端 tag 前缀 `desktop-v*`，CI 校验 `desktop/package.json` 版本一致后构建并发布到**本仓库** Releases；
- `desktop/package.json` 的 `build.publish` 指向 `qqww45/nova-admin`（合并前的 `qqww45/hengzhang` 已失效，务必保持同步）；
- 客户端 `electron-updater` 默认读取 GitHub Releases 的 `latest.yml`：
  - 仓库需为 **public**（私有仓库需内置 token，不可接受）；
  - 国内下载慢的情况，可切换为 `generic` provider 指向自有静态目录（EdgeOne/服务器），只需改 `publish` 配置，客户端逻辑不变。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 金蝶 WebAPI 许可/并发限制 | 客户环境用业务员账号实测；上报限流 + 错峰 |
| 业务员数据天然残缺 | 已接受，产品说明中讲清；系统不补偿 |
| 增量发现不了物理删除 | 服务端下发 `sync.full` 全量指令兜底 |
| SQLite 并发写锁 | 开 WAL + 上报串行 + 重试；切 MySQL 仅改 profile |
| 令牌泄露 | DB 存 hash、可吊销、绑定页可见 |
| 老客户端仍在本地对账 | 过渡期双写，M2 完成后下线 |
| 版本碎片 | 客户端自动更新 + WS 可推 `client.update` |

### 12.2 与上述方案的偏差（实现时确定，均已在代码注释说明）

1. **接口前缀**：方案 §4.1 写 `/api/kd/...`；实际为 `/kd/...`，`/api` 由前端 dev 代理与网关剥离（与现有全部接口一致）。
2. **多了 `kd_binding_code` 表**：绑定码只存 SHA-256 摘要 + 过期时间，靠 `used_at IS NULL` 做一次性抢占，避免"拿到库就能换令牌"。
3. **分录幂等键兜底**：部分账套取不到 `FEntryID`/`FEntity_FEntryID` 时，服务端用 `outbound_fid * 100000 + 单内行序号` 生成稳定键（`KdOutboundLine.resolveEntryId`）。序号按单据各自累加，**不能用请求数组下标**——分块上报时第二块会从 0 重来并覆盖同单其它行（客户端已在切块前算好）。
4. **水位语义**：客户端上报的 `watermarkTo` 是"本次上行的本地完成时间"，服务端只做单调推进与展示；接入 `FModifyDate` 双水位后改为金蝶修改时间。
5. **金额口径**：表头 `amount_cents` 一律由服务端按本批次分录重算；对账单页同样以分录为准，无分录的单据才退回表头金额（页面上会标注"该单无分录数据"）。
6. **全量差集**：`mode=FULL` 的批次在 `finish` 时把本批次未见到的单/分录标记 `invalid=1`；重新出现的行在 upsert 时自动复位为 0。
7. **对账单不落库（M2 调整）**：方案原写"接入现有 `biz_statement` 口径"，实现改为**实时计算 + 导出**，不写 `biz_statement`。原因：`biz_statement.customer_id` 指向本系统 `biz_customer`，而采集器上报的是金蝶客户内码，两套客户体系没有映射，硬接会污染现有应收账龄与确认流。KD 对账单只需要"这段期间出了多少货"，无期初/收款/确认诉求。
8. **指令通道用轮询而非 WebSocket（M4 调整）**：指令落 `kd_command` 队列，客户端 15 秒短轮询取走并回执。现场多在客户内网反向代理后面，长连接会被中间设备掐断；采集器还可能休眠数小时。落库 + 轮询在断网重连后不丢指令，消息形态（command + payload + ack）与 WS 一致，将来换传输层不影响业务代码。
9. **服务端字段集只是"候选之一"（M3 调整）**：`buildLineCandidates` 的优先级为本机自检结果 → 服务端任务清单 → 草稿 → 内置候选。客户 / 订单的字段解析按位置取下标，服务端改顺序会错列，因此**只对出库分录启用服务端字段集**。
10. **对账单查询窗口**：默认最近 90 天、单次最多 366 天，避免"不填日期就全表扫"。
