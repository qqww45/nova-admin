# 人机验证方案（替代图形验证码）

> 定位：替换现有「图形验证码输入」方案，解决两个问题 —— **安全性不足**（静态图像可被识别、票据可被重放、失败无惩罚）与**体验差**（人人都要读图打字，移动端与无障碍场景尤其糟糕）。
> 本文只描述机制与流程，不涉及具体技术选型与实现细节。

---

## 1. 方案目标

| 目标 | 含义 | 衡量口径 |
|---|---|---|
| 无感优先 | 正常用户**大多数时候什么都不用做** | 无感通过率（无需任何交互即完成的占比） |
| 必要才打扰 | 只在风险信号异常时才要求验证，且交互极轻 | 挑战触发率、挑战一次通过率 |
| 机器难通过 | 让"识别 + 重放 + 爆破"三条路都失效 | 机器流量拦截率、打码/自动化成功率的下降 |
| 人人可用 | 移动端、弱视/无障碍、弱网都能完成 | 挑战完成率、放弃率、无障碍通道使用率 |
| 可运营 | 阈值可灰度、效果可观测、误杀可申诉 | 误杀率（正常用户被挑战比例）、申诉量 |

**设计原则**：验证强度与风险等级匹配 —— 低风险零验证，中风险轻验证，高风险强验证。把"安全成本"花在少数可疑请求上，而不是让所有用户共同承担。

---

## 2. 核心机制

### 2.1 三层验证强度（风险分层，而非一刀切）

| 等级 | 触发条件（示例信号） | 用户动作 | 说明 |
|---|---|---|---|
| L0 无感 | 已信任设备 + 环境正常 + 频次正常 + 来源稳定 | **无** | 凭据正确即通过，不展示任何验证控件 |
| L1 轻验证 | 陌生设备、来源网络变化、频次略高、环境有轻微异常 | **一次按压 / 一次滑动**（约 1 秒，无文字输入） | 判定依据是"完成动作的过程"，而非"看清了什么" |
| L2 强验证 | 多次失败、明显自动化特征、异地/异常时段、批量特征、敏感操作 | **第二因子**（一次性码 / 生物识别确认） | 同时向账号所有者推送安全提醒 |

信号来源（只采集判定必需的最小集合，不采集用户输入内容与页面行为内容）：设备信任状态、来源网络与地理/运营商稳定性、请求频次与失败序列、运行环境一致性（是否存在自动化特征）、账号历史行为基线。

### 2.2 挑战的四个性质（这是安全性的关键）

1. **一次性**：每次挑战由服务端签发唯一票据，用后即焚，不能二次使用。
2. **强绑定**：票据绑定「账号 + 设备 + 会话 + 时间窗」四要素，任一变化即失效（换个会话/IP 拿去用无效）。
3. **短时效**：有效期以分钟计，超时自动作废，压缩可攻击窗口。
4. **服务端判定**：前端只负责采集"完成过程"的特征，结论由服务端给出；前端不存在"正确答案"，也就没有可窃取的标准答案。

> 抗重放的实现要点：验证请求必须携带票据，服务端以**原子方式**消费（同一票据并发提交只有一次成功），重复提交直接判失败并计入风险分。

### 2.3 防机器识别

| 手段 | 解决的问题 |
|---|---|
| 判定"过程"而非"图像" | OCR / 打码平台拿到的是一张图，而通过与否取决于交互过程的时序与连续性特征，静态信息无用 |
| 挑战随机化 | 每次形态与参数不同，无法预先计算答案或批量复用 |
| 服务端出结论 | 前端无可被逆向的固定答案与判定逻辑 |
| 环境完整性校验 | 识别出自动化运行环境与脚本化行为，直接提升风险等级 |
| 多层叠加 | 环境 + 行为 + 速率 + 设备信任任一被绕过，其余仍在生效，避免单点依赖 |

### 2.4 防暴力破解

- **统一失败计数**：凭据失败与挑战失败计入同一套计数，杜绝"反复刷新验证码直到刷到简单的一张"或"绕过验证只爆破密码"。
- **指数退避 + 临时锁定**：连续失败后逐步延长冷却时间，达到阈值锁定账号与来源（阈值与锁定时长按业务敏感度配置）。
- **分层限流**：账号维度、来源网段维度、全局维度分别限流，防止"换账号不换 IP"和"换 IP 不换账号"两种打法。
- **越打越难**：失败次数提升风险等级，攻击者的每一次尝试都会让下一次更难（L0 → L1 → L2）。
- **防账号枚举**：验证失败的响应与"账号不存在/密码错误"保持不可区分，避免被用来探测账号是否存在。

### 2.5 与「可信设备」协同

已信任设备是最强的免验证信号：

```
已信任设备 + 无异常  → L0 无感（现有"30 天免验证"升级为"无需任何交互"）
陌生设备   + 无异常  → L1 轻验证（一次按压即可，并可选择信任此设备）
陌生设备   + 异常    → L2 强验证
已信任设备 + 异常    → L1/L2（信任不等于无条件放行，异常信号可临时提升等级）
```

## 3. 交互流程

### 3.1 登录（主流程）

```
1. 用户输入账号密码并提交（页面上默认不显示任何验证控件）
2. 服务端评估风险等级
   ├─ L0：直接返回登录成功                          ← 用户零操作
   ├─ L1：返回"需要轻验证" + 一次性票据
   │      页面出现极简控件（按住/滑动一次，约 1 秒）
   │      用户完成 → 连同票据一起提交 → 成功
   └─ L2：返回"需要强验证" → 第二因子（一次性码/生物识别）→ 成功
3. 失败处理：换新票据；失败计数 +1；达阈值冷却/锁定；提示语不区分具体原因
4. 通过后可选「信任此设备」，此后在该设备上长期免验证
```

### 3.2 敏感操作（改密、换绑、支付类）

即使会话已登录，也执行 **step-up 重新验证**：按操作敏感度直接要求 L1 或 L2，验证结果只在**本次操作**有效，不提升整个会话的信任级别。

### 3.3 降级与无障碍

| 场景 | 处理 |
|---|---|
| 无脚本环境 / 控件加载失败 | 自动降级到一次性码通道（邮件/短信），保证一定有一条可完成路径 |
| 视觉障碍 | 提供非视觉替代（音频或键盘可达的等价挑战），不允许出现"只有一种感官可完成"的验证 |
| 弱网 / 老年用户 | 挑战超时自动换新；允许有限次重试；提供人工申诉通道 |
| 误判（正常用户被反复挑战） | 「信任此设备」一键解除；申诉通道人工处理 |

## 4. 适用场景

| 场景 | 推荐强度 | 理由 |
|---|---|---|
| 常规登录（已信任设备） | L0 无感 | 体验最优，风险已被设备信任覆盖 |
| 常规登录（陌生设备/新环境） | L1 轻验证 | 首次登录需确认"是本人"，之后可信任 |
| 密码错误后的重试 | L1 → 逐步升到 L2 | 失败序列本身就是风险信号 |
| 改密、换绑手机/邮箱、资金类操作 | L2 强验证（step-up） | 后果严重，需独立二次确认 |
| 批量/异常来源、自动化特征 | L2 + 限流 + 告警 | 直接拦截并留痕 |
| 内部/低风险后台（可选） | L0 + 频次基线 | 以行为基线替代验证，减少打扰 |

## 5. 相较现有方案的改进

### 5.1 易用性

| 维度 | 现有图形验证码 | 新方案 |
|---|---|---|
| 正常用户负担 | 每次都要读图 → 手输 4 位 | 大多数时候**零操作**；需要时一次按压 |
| 输入成本 | 看图 → 切键盘 → 逐字输入，移动端尤差 | 无文字输入、无键盘切换，单手可完成 |
| 易错率 | 字符易混淆（0/O、1/l），输错需整张重来 | 无识别负担，几乎不存在"看错" |
| 无障碍 | 弱视/色弱用户基本无法独立完成 | 提供非视觉等价通道 |
| 失败体验 | 重新加载并再输一次 | 自动换新挑战，且失败即触发更强防护 |

### 5.2 安全性

| 攻击手法 | 现有图形验证码 | 新方案 |
|---|---|---|
| OCR / 打码平台识别 | **有效**：答案是图像里的字符，识别即可通过 | **失效**：通过与否取决于交互过程与服务端判定，静态图像无用 |
| 重放票据 | 若票据未在服务端原子消费，可复用 | **失效**：票据一次性 + 四要素绑定 + 短时效 + 原子消费 |
| 暴力破解 | 刷新验证码不受惩罚，可无限试 | **失效**：统一失败计数、指数退避、分层限流、越打越难 |
| 账号枚举 | 响应差异可能被利用 | **失效**：统一不可区分的错误响应 |
| 凭据填充（撞库） | 撞对密码后只需过一次图检 | **更难**：撞库来源具备批量特征 → 直接升到 L2 |
| 绕过验证直接爆破密码 | 验证与密码可分离尝试 | **失效**：挑战失败与凭据失败统一计数 |

| 指标 | 期望方向 | 说明 |
|---|---|---|
| 无感通过率 | 上升（目标：绝大多数正常登录零交互） | 体验改善的主指标 |
| 挑战触发率 | 下降 | 说明打扰集中在真正的可疑请求 |
| 挑战一次通过率 | 高（人类几乎一次过） | 过低说明交互设计或阈值有问题 |

| 机器流量拦截率 | 显著上升 | 安全收益主指标 |
| 误杀率（正常用户被挑战比例） | 可控且持续下降 | 靠灰度调阈值 + 设备信任收敛 |
| 单一来源短时请求峰值 | 被压平 | 限流与退避生效 |

## 7. 风险与边界（必须提前说明）

1. **误判不可避免**：共享出口网络、隐私模式、弱环境特征的用户更容易被判为高风险。缓解：设备信任一键解除 + 申诉通道 + 阈值灰度。
2. **冷启动数据不足**：行为基线建立前，风险分不准。缓解：上线初期阈值从严（宁可多挑战），随数据积累逐步放宽。
3. **不能单点依赖**：任何单一信号都可能被绕过，必须靠「环境 + 行为 + 速率 + 设备信任」多层叠加。
4. **隐私与合规**：只采集判定必需的最小信号，明确留存期限与用途，不采集用户输入内容与页面内容，并向用户明示。
5. **可用性优先原则**：任何验证都必须留有可完成的降级路径；宁可放宽一次，不可让用户卡死在登录页。

### 8.2 时序

```
POST /login（账号密码 + 设备标识）
   ├─ 凭据错误 → 统一提示 + 失败计数（防账号枚举、防爆破）
   └─ 凭据正确 → 风险评级
        ├─ NONE   → 直接返回令牌（零操作）
        ├─ LIGHT  → 1014 + 票据 → 用户按压 1 秒 → POST /login/verify（票据 + 过程特征）
        └─ STRONG → 1015 + 票据 → POST /login/code 下发一次性码 → POST /login/verify（票据 + 码）
                                  （轻验证做不了时可降级为这条路径，会换发新票据）
```

### 8.4 已知边界

- 票据与一次性码目前为**内存实现**：重启应用后票据失效（表现为重新验证一次）；多实例部署需换 Redis（接口注释已给出 GETDEL / Lua 方案）。
- 一次性码发送已实现**双通道**（端口化 `OneTimeCodeSender`）：开发环境 `log`（回传验证码便于自测），生产 `email`（走通用 `EmailService` + SMTP）。
  三层防护防止"发布时忘了改"：① 主配置默认取安全值（email + 不回传）；② `application-dev/prod.yml` 按 profile 覆盖；③ `VerifyConfigGuard` 在生产启动时校验，配错直接拒绝启动。详见 `README.md`。
- 滑块判定是"提高成本"的一层，不是银弹；它与环境识别、速率限制、设备信任叠加生效。
  - 自研拼图与商业方案的差距：商业方案（极验/Turnstile/防水墙）真正值钱的是**风控模型和海量样本**（设备指纹、行为基线、信誉库），UI 只是载体；本方案用滑块拼图+轨迹评分已是定位合理的轻验证，但**真实浏览器+拟人脚本**的挑战依然可能通过；
  - 自研拼图本身有"缺口可被图像识别"的攻击面，但因为我们同时要求轨迹评分（位置关+轨迹关双层），识别出缺口坐标后还要拟出像样的拖动曲线，**单点攻破不再成立**；
  - 强化路线：① 接入商业验证（Turnstile/hCaptcha/极验）拿到厂商模型；② 强化风控信号（设备指纹、IP 信誉、行为基线）；③ 调严阈值（收益小、误杀明显，不建议）。
- 误判处理：被判强验证时可选择「信任此设备」；滑块不可用时走一次性码降级；阈值集中在 `LoginRiskEvaluator` 与 `HumanInteractionVerifierImpl`，可灰度调整。

### 8.5 环境配置与安全默认值（防"发布时忘了改"）

这套机制的风险在于：**配错了系统照样能跑**（验证码被打印到日志、随响应回传，功能看起来正常）。
因此不依赖"人记得改"，而是三层防护：

| 层 | 措施 | 效果 |
|---|---|---|
| 1. 安全默认值 | 主 `application.yml` 默认 `channel=email`、`reveal-code=false` | 任何未显式配置的 profile 落到的是安全值 |
| 2. profile 覆盖 | `application-dev.yml` 覆盖为 `log` + `true`（开发便利）；`application-prod.yml` 显式写安全值 | 切 profile 即切换，无需手工改开关 |
| 3. 启动期校验 | `VerifyConfigGuard`（仅 prod 生效）校验：reveal-code 必须 false、channel 不能是 log、mail 三项必填 | **配错 = 起不来**，而不是带病上线 |

邮件服务配置位置：`application.yml` 的 `spring.mail.*`，敏感值用环境变量注入
（`MAIL_HOST` / `MAIL_USERNAME` / `MAIL_PASSWORD` / `MAIL_FROM` / `ADMIN_VERIFY_CHANNEL` / `ADMIN_VERIFY_REVEAL_CODE`）。

上线命令：`mvn spring-boot:run -Pprod -Dspring-boot.run.profiles=prod`
（注意 `-Pprod` 只是 Maven profile，**必须**同时用 `-Dspring-boot.run.profiles=prod` 才会让应用激活 prod）。
