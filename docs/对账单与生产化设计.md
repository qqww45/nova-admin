- 日期：2026-10-22
- 作者：AI 助手（基于代码审计 + 用户样本 `一恒科&鸿晟达 对账20261015.xlsx`）
- 状态：待用户确认后进入实施

---

## 0. 背景与目标

当前系统已实现客户 / 订单 / 出货三大域，但"对账"只是订单明细上的一个 `reconcile_date` 日期标记位，没有任何对账单主表、收付款流水、应收余额。用户要求：

1. **补齐"对账单"功能**，并以真实业务样本（深圳一恒科电子科技有限公司 对客户的对账单）为基准，按行业通用方法实现。
2. **对整个业务系统做生产化梳理**，使其达到"真实环境可用"。

样本对账单的结构（已解析确认）：

- 表头：我方公司抬头（名称/英文名/地址/电话/传真/印章）、对账标题、**客户名称 / 联系人 / 联系方式 / 地址 / 对账日期**。
- 明细列：`日期 | 出货单号 | 客户订单号 | 物料编号 | 物料名称 | 规格 | 单位 | 数量 | 单价 | 金额 | 备注`。
  - 出货为正（`XSCKD…`），**退货为负**（`XSTHD…` 销售退货、`CGTL…` 退工厂返工，数量/金额均为负，自动冲减）。
  - 备注内联物流单号、关联单号（"单号：XSCKD…"）。
- 尾部：累计订单送货汇总 + **收款记录**（`26/1/31 收：990000 元 分 254888 元`）+ 期末应收余额。

结论：这是一份标准**客户应收账款对账单**，恒等式为：

```
期末应收 = 期初应收 + 本期出货 − 本期退货/退厂 + 本期收款
```

## 1. 范围

### 纳入（In）
- 收款登记域（手工录入，预留银行/财务导入接口）。
- 期初应收余额入口。
- 对账单生成（按客户 + 期间，实时计算预览）、签发快照、客户确认/差异标记。
- 对账单 Excel 导出（对齐样本传统台账格式）。
- 生产化 6 项加固（见第 4 节）。

### 不纳入（Out）
- 银行直连 / 自动认领收款（仅留导入接口位）。
- 发票开具（仅记录发票号字段）。
- 多币种复杂折算（仅支持单币种对账单，币种来自字典）。

## 2. 术语对齐

沿用《系统提示词》第 2 节：**客户、出货、退货、单价（含税/不含税）、金额（价税合计/不含税/税额）**。新增术语：

| 术语 | 含义 |
|---|---|
| 收款 | 客户回款，减少应收 |
| 期初应收 | 对账周期开始前的历史欠款 |
| 对账单 | 某客户在某期间内的应收交易明细与余额快照 |
| 签发 / 确认 | 我方生成 → 发给客户 → 客户回签（或标记差异） |

### 3.2 出货表扩展（V13 附改造，影响既有数据）

当前 `biz_shipment` 仅有"出货 + 作废红冲"，无退货/退厂方向。样本对账单要求把 `XSTHD`（销售退货）、`CGTL`（退工厂）作为负数行。设计决策（我的判断）：

- 给 `biz_shipment` 新增 `shipment_type varchar(20)`：`出货 / 退货 / 退厂`，默认历史数据回填为 `出货`。
- `qty` / `amount` 仍按既有正向存储，负值表示退货/退厂（与样本一致）。
- 作废（红冲）逻辑不变；退货单本身也可作废。
- 此改动需配套更新：`ShipmentAppService` 保存、导入映射、前端出货页"新增退货/退厂"入口（第二阶段）。

### 3.3 核心域逻辑（`domain/service/StatementGenerator`，必须有单元测试）

```
ending_balance = opening_balance
               + Σ(shipment.amount where customer, biz_date ∈ [start,end], status=正常)   // 含出货(+)/退货(−)/退厂(−)
               − Σ(receipt.amount   where customer, receipt_date ∈ [start,end], status=正常)
```
- 预览：`POST /biz/statement/preview` 按客户+期间实时聚合，返回 `lines[]` + 四要素汇总，**不落库**。
- 生成快照：`POST /biz/statement` 把预览结果写入 `biz_statement` + `biz_statement_line`，`status=草稿`，写 `operation_log`。
- 签发：`PUT /biz/statement/{id}/issue` → `已签发`。
- 确认：`PUT /biz/statement/{id}/confirm`（回签，`已确认`）或 `mark-diff`（`有差异`，记录差异说明）。
- 导出：`GET /biz/statement/export?id=...` 复用现有 `XlsxWriter`，输出样本同款传统台账格式（含抬头、明细、汇总、收款段），导出上限沿用 5000 行。

## 4. 生产化第二条线（代码审计结论）

按严重程度排序，均需随对账单并行实施：

1. **数据备份**：`deploy/` 增加定时 `mysqldump`/卷快照脚本 + 上线清单条目；SQLite 仅限 dev/staging。
2. **业务表数据权限**：将 `@DataScopeAnno` 接入 `biz_customer/order/shipment`（及新表），实现业务员"仅本人数据"，字典/配置化管理数据范围。
3. **幂等与并发发货**：`biz_shipment` 加 `@Version` 乐观锁；修复 PostgreSQL 大事务"aborted"连坐（逐行独立事务或 savepoint）；唯一索引遇 NULL 失效——将幂等键中可空列补默认值或改用应用层去重（`ShipmentRepository.findByIdempotentKey` 接回调用）。
4. **审计补全 + 错误清单**：订单创建/改价/确认/取消/对账、客户增删改补写 `operation_log`；导入 `BatchLineResult.fail` 回填 `errorField/rawData`，使错误清单 xlsx 可定位列。
5. **禁止物理删除**：订单/明细 `remove/removeItem` 改用 `@TableLogic` 软删除，与"禁止物理删除业务数据"红线一致；保留软删除+回溯。
6. **报表与精度**：`ReportAppServiceImpl` 改用 SQL GROUP BY 分页聚合；上线前切 MySQL/PostgreSQL 并复核 SQLite REAL 造成的金额漂移；对账/账龄纳入报表。

## 6. 决策记录（我的判断，可在确认时推翻）

- 收款采用**系统内手工登记**（方案 1），预留导入接口。✅ 已与用户确认方向。
- 对账单 = **期间快照 + 明细流水**，生成后落库可签发，而非每次实时算。
- 退货/退厂通过在 `biz_shipment` 增加 `shipment_type` 表达（需回填历史数据）。
- 收款先做到**客户级**，分配（"分 254888 元"）留接口，不在 v1 强约束。
