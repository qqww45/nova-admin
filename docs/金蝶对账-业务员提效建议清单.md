# 金蝶对账 · 业务员提效建议清单（P0 / P1 / P2）

> 基于 2026-11-03 的全链路梳理（桌面采集器 → 落库 → 对账单/导出），从业务员日常使用视角
> 给出的改进建议。链路健康结论、已修项与回归结果见文末附录及 PR 描述；
> 本文档聚焦"还能加什么来解决实际问题"。优先级口径：
> **P0** = 日常高频痛点、成本低，应尽快做；**P1** = 明确价值、中等成本，排期做；**P2** = 大功能，先方案后立项。

## 业务员的一天（痛点来源）

1. 月底/季度对账：按客户出对账单 → 发客户核对 → 回签 → 提开票/催款；
2. 客户说"数字对不上"：要自己排查是数据没同步上来、单据作废、还是无分录退了表头金额；
3. 换了台电脑 / 采集器没开机：数据断档，网页上却看不出来原因；
4. 同名物料分不清规格，客户对不上数要来回打电话。

## P0（低成本高价值，本 PR 已顺手落地两项 + 一项修复）

| # | 建议 | 解决的实际问题 | 价值 / 难度 | 状态 |
|---|------|----------------|-------------|------|
| 1 | **规格型号（spec）断链修复** | 对账单导出与数据查看页的「规格型号」列此前永远为空——采集侧从未采这个字段。同名物料不同规格对不上数，是业务员与客户核对时的高频障碍 | 价值高 / 难度低（桌面端候选字段 + 本地库列 + 上行透传，服务端本就支持） | ✅ 本 PR 已修，含回归测试 |
| 2 | **明细页一键「导出该客户对账单」** | 业务员最常见动作就是"给某一个客户出单"，此前只能回列表改条件后点全局导出，文件里还混着所有客户 | 价值高 / 难度极低（复用既有 export 接口，传 `customerFid` 即可） | ✅ 本 PR 已实现 |
| 3 | **绑定页「采集器在线」状态** | "数据没上来"十有八九是采集器没开机/没联网，此前业务员无法自查，只能找管理员翻指令记录。按指令轮询心跳（`lastUsedAt`，15 秒一轮）即可判定 | 价值高 / 难度极低（数据已有，纯前端展示） | ✅ 本 PR 已实现 |
| 4 | 汇总页月份快捷选择（本月 / 上月 / 近 3 月） | 对账基本按月发生，目前每次都要手动点日期区间 | 价值中 / 难度极低（`el-date-picker` shortcuts） | 建议（半天的前端小改，可与任一前端需求搭车） |

## P1（明确价值、中等成本，建议排期）

| # | 建议 | 解决的实际问题 | 思路与工作量 | 风险 |
|---|------|----------------|--------------|------|
| 1 | **双水位增量（FModifyDate − 15min 缓冲 + 每月按 FDate 回看 30 天）** | 现在增量按 `FDate` 过滤，**改过的历史单抓不到**（改单号/改数量后网页数字与金蝶不一致）；全量兜底又太重。方案 §3.1 的"目标形态"一直未实施 | 桌面端 `sync/runner.ts` 增量条件改为 `FModifyDate >= 水位-15min`，另跑一条按 `FDate` 的月度回看；服务端水位语义从"本地完成时间"切换为金蝶修改时间（表结构已预留 `watermark_field` 与 `kd_modify_time`）。桌面端为主，约 2~3 天 | 水位切换需要客户端发版配合；灰度期保留旧逻辑开关 |
| 2 | **对账单汇总/导出补充金蝶客户编码列** | `kd_customer.kd_number` 已同步但汇总/导出只显示客户名称，**重名客户**容易串户；客户按编码核数比按名称快 | `KdStatementRepository.listBills` 关联 `kd_customer`（账套+内码）取编码，导出两个 sheet 与汇总页各加一列。约 1 天 | 低；注意账套内关联（金蝶内码不跨账套唯一） |
| 3 | **数据体检报告（无分录单据清单）** | "无分录单据退回表头金额"金额口径不透明，对不上时业务员不知道从哪查起；目前要自己到出库数据页按分录行数=0 过滤 | 汇总页顶部加一条体检条幅（本期无分录 N 张、作废 M 张、失效 K 张，点击跳转对应过滤视图）。约 1~2 天 | 低；纯读侧聚合 |
| 4 | **采集器托盘常驻 + 定时同步** | 电脑重启后采集器不启动 → 数据断档数天没人发现（方案 §12.3 已列为未实施）。配合在线状态列，让断档在第一天就暴露 | Electron tray + `powerMonitor` + 定时触发 `runSync`；多台机器重复全量问题用服务端水位协商（绑定行水位已具备）。约 2~3 天 | 需要图标资源与休眠场景实测 |
| 5 | **对账单 PDF/盖章模板** | 客户要求"盖章对账单"时业务员只能手工二次加工 Excel；方案 §12.3 明确"客户提出时再接模板引擎" | 服务端 HTML 模板 → PDF（或复用 XlsxWriter 生成固定格式 + 打印视图）。约 2~3 天 | 模板样式需要客户确认，先收集 1~2 个样板再动工 |

## P2（大功能，先方案后立项）

| # | 建议 | 解决的实际问题 | 思路概要 |
|---|------|----------------|----------|
| 1 | **金蝶出库 vs 本系统出货单交叉核对** | 本仓库已有 客户/订单/出货 业务系统，出货数据与金蝶出库分录是同一批货的两个口径；两边金额/数量不一致要等客户发现。按「源单编号/物料+数量+日期」匹配做差异报告，让业务员在出对账单前先自查 | 新增只读比对页：取本系统 shipment 明细与 kd_outbound_line 按客户+期间匹配，输出"金蝶有我无 / 我有金蝶无 / 数量金额不一致"三类差异。涉及两套客户体系的映射（本系统 biz_customer ↔ 金蝶客户内码），需要先做映射维护页 |
| 2 | **应收单 / 收款单同步** | 业务员对完出货后，"客户到底付了多少"仍要回金蝶看；对账单只有出货口径，没有回款口径 | 采集器加两个任务（`AR_receivable` / 收款单），复用现有任务清单机制——这正是"新增单据类型 = 后台加一条任务 + 一张表 + 一个页面，客户端不发版"设计的试金石 |
| 3 | **对账单确认流（客户回签留痕）** | 客户口头/微信确认后没有留痕，月底扯皮时拿不出"客户已确认"的证据；本系统 biz_statement 的确认流不适用于 KD 口径（方案 §12.2 第 7 条），需独立轻量实现 | 对账单快照落库（防后续同步改数）+ 上传回签扫描件/客户邮箱确认链接；先做快照落库，确认方式按现场反馈选型 |
| 4 | **业务员月度归档与自助分享** | 每月对账单散在业务员本地 Excel 里，换电脑即丢；主管想看"这个月各业务员对账情况"没有入口 | 导出前先把当期口径快照存服务端（按人+客户+月份），个人页可随时回看历史版本；分享链接给客户自助查看（带有效期与水印） |

## 不建议做的（讨论中已否决或明确不做）

- **WebSocket 指令通道**：现场反向代理 + 采集器休眠场景下轮询更可靠，方案 §12.2 第 8 条已论证，维持现状；
- **跨业务员数据合并 / 上级看下级**：方案 §1 明确不做，权限模型（data_scope=4 仅本人）不为其留口子；
- **把 KD 对账单接入 `biz_statement` 应收口径**：两套客户体系无映射，方案 §12.2 第 7 条已论证并否决。
